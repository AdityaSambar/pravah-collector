## 1. Project Overview

### 1.1 Purpose

Pravah Collector is a background data collection service that periodically queries Uber's fare estimation API for directional route pairs across the Bengaluru metro network. The data trains a ride price prediction ML model for auto rides between metro stations and surrounding hotspots.

### 1.2 Commute Model

The pattern being captured is:

```
hotspot → [auto] → metro exit → [metro] → metro exit → [auto] → hotspot
```

Only the **auto legs** are collected. This means:
- We only query AUTO product fares (productClassificationTypeName = "AUTO")
- We never collect station-to-station pairs
- Each pair is bidirectional: hotspot→station and station→hotspot are separate records

### 1.3 Scope of This Document

This document covers the **Collector** component only. The ML model architecture and frontend dashboard implementation are out of scope.

### 2.2 Workers

- Multiple identical Spring Boot background worker instances deployed on Render
- Each worker is assigned a fixed slice of route pairs via the coordinator
- Workers communicate **exclusively through Supabase** — no direct inter-worker communication
- Workers use Java 21 virtual threads for concurrency — multiple pairs can be queried concurrently within a single worker process without blocking OS threads
- Each worker runs a heartbeat loop (every 60 seconds) to signal liveness to Supabase

### 2.3 Coordinator

- One worker at a time acts as coordinator (leader)
- The coordinator role is lightweight — it does not collect fares differently, it just additionally runs assignment and health-check logic
- Responsibilities:
    - Assign unassigned pairs to workers
    - Detect stale workers (heartbeat missed > 5 minutes)
    - Reassign pairs from stale workers to healthy ones
    - Pick up new pairs inserted by a station JSON hot-reload
    - Reset DORMANT pairs whose `dormant_until` has passed

### 2.4 Route Pairs

A route pair is a unique combination of:

| Component | Description |
|---|---|
| `hotspot_hex_id` | H3 resolution-8 hex ID of the pickup/dropoff area |
| `station_id` | Metro station ID (e.g. PL19) |
| `exit_label` | Specific exit gate (e.g. Gate A) |
| `direction` | `HOTSPOT_TO_STATION` or `STATION_TO_HOTSPOT` |

Pairs are generated by `generate_hotspots.py` from `metro_stations.json` and seeded into Supabase. Estimated total pairs at full network coverage: **4,000–8,000**.

### 2.5 Timeslots

Collection runs **05:00–23:00 IST** (metro operational hours), divided into **36 thirty-minute timeslots** indexed 0–35:

| Index | Time (IST) | Weight |
|---|---|---|
| 0 | 05:00–05:30 | 1x |
| 1 | 05:30–06:00 | 1x |
| 2–9 | 06:00–10:00 | **2x (morning rush)** |
| 10–23 | 10:00–17:00 | 1x |
| 24–31 | 17:00–21:00 | **2x (evening rush)** |
| 32–35 | 21:00–23:00 | 1x |

Rush hour timeslots (2–9 and 24–31) carry **2x weight** in the station readiness score.

## 3. Technology Stack

| Layer | Technology | Rationale |
|---|---|---|
| Backend | Spring Boot 3.x + Java 21 | Virtual threads for IO-bound concurrency, familiar stack |
| Database | Supabase (Postgres) | Free tier, no expiry, 500MB, managed |
| Hosting | Render Background Workers | $7/mo per worker, no per-seat fees (as of 2026) |
| Geo indexing | H3 Resolution 8 | ~460m hex diameter, well-suited for auto ride distances |
| HTTP client | Spring WebClient or RestClient | Non-blocking, works well with virtual threads |
| Alerts | SMTP / SendGrid free tier | 100 emails/day free, sufficient for alert volume |
| Build | Maven | Already in project setup |

### 3.1 Java 21 Virtual Threads

Since collection is almost entirely IO-bound (waiting on Uber API responses), virtual threads are ideal. Enable them in Spring Boot with:

```yaml
# application.yml
spring:
  threads:
    virtual:
      enabled: true
```

This lets you run dozens of concurrent pair queries in a single worker process on a $7/month Starter instance (512MB RAM, 0.5 vCPU) without running out of threads.

## 4. Data Model

### 4.1 `fare_records` — Raw collection table

```sql
CREATE TABLE fare_records (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    hotspot_hex_id   VARCHAR(20) NOT NULL,
    station_id       VARCHAR(10) NOT NULL,
    exit_label       VARCHAR(50) NOT NULL,
    direction        VARCHAR(25) NOT NULL CHECK (direction IN ('HOTSPOT_TO_STATION', 'STATION_TO_HOTSPOT')),
    fare_inr         NUMERIC(8, 2) NOT NULL,
    surge_multiplier NUMERIC(4, 2) NOT NULL DEFAULT 1.0,
    eta_min          SMALLINT,
    timeslot         SMALLINT NOT NULL CHECK (timeslot BETWEEN 0 AND 35),
    collected_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    worker_id        VARCHAR(50) NOT NULL
);

CREATE INDEX idx_fare_records_pair ON fare_records (station_id, exit_label, hotspot_hex_id, direction, timeslot);
CREATE INDEX idx_fare_records_collected_at ON fare_records (collected_at);
```

**What we extract from the Uber response:**

| Field | Source in Uber JSON |
|---|---|
| `fare_inr` | `upfrontFare.fare` (AUTO product only) |
| `surge_multiplier` | `dynamicFareInfo.multiplier` |
| `eta_min` | `etaInMin` |

Everything else is metadata we add at collection time.

### 4.2 `pair_eligibility` — Collection state per pair per timeslot

```sql
CREATE TABLE pair_eligibility (
    pair_id           VARCHAR(120) NOT NULL,  -- composite key: station_id|exit_label|hex_id|direction
    timeslot          SMALLINT NOT NULL CHECK (timeslot BETWEEN 0 AND 35),

    dormant_until     TIMESTAMPTZ,
    worker_id         VARCHAR(50),            -- null = unassigned
    last_collected_at TIMESTAMPTZ,
    PRIMARY KEY (pair_id, timeslot)

CREATE INDEX idx_eligibility_worker ON pair_eligibility (worker_id, status);
CREATE INDEX idx_eligibility_unassigned ON pair_eligibility (status) WHERE worker_id IS NULL;
```

## 5. Collection Engine

### 5.1 Collection Loop

Each worker runs a continuous loop:

```
while (running) {
    currentTimeslot = getCurrentTimeslot()           // derived from IST time
    if (outsideOperatingHours()) { sleep(60s); continue; }

    activePairs = getAssignedActivePairs(workerId, currentTimeslot)
    if (activePairs.isEmpty()) { sleep(60s); continue; }

    for each pair in activePairs (via virtual threads):
        fare = queryUberAPI(pair)
        if (fare != null):
            persist(fare)
            incrementSampleCount(pair, currentTimeslot)
            if (sampleCount >= targetX):
                markDormant(pair, currentTimeslot)

    sleep(baseDelay + jitter)
}
```

### 5.2 Timeslot Calculation

```java
public static int getCurrentTimeslot() {
    ZonedDateTime now = ZonedDateTime.now(ZoneId.of("Asia/Kolkata"));
    int minutesSince5am = (now.getHour() * 60 + now.getMinute()) - (5 * 60);
    if (minutesSince5am < 0 || minutesSince5am >= 36 * 30) return -1; // outside window
    return minutesSince5am / 30;
}
```

### 5.3 Jitter & Rate Limiting

All inter-request delays follow this formula:

```
baseDelay = config.min_request_delay_ms          // default: 10,000ms
jitterRange = baseDelay * (config.max_jitter_pct / 100)
actualDelay = baseDelay + random(-jitterRange, +jitterRange)
```

Additionally:
- Requests are not sent at exact clock boundaries (no synchronization between workers)
- Each worker independently computes its own delay schedule
- A small startup jitter (0–30s random) is applied before the first request to prevent all workers hitting the API simultaneously on deploy

### 5.4 Retry & Backoff

On a failed Uber API call:

```
attempt 1: immediate retry
attempt 2: wait 5s + jitter
attempt 3: wait 15s + jitter
attempt 4: wait 60s + jitter
attempt 5+: wait 5min + jitter, increment consecutive_failure_counter
if consecutive_failure_counter >= threshold: trigger alert, pause worker for 10min
```

HTTP 401 / token invalidation: **no retry**. Immediately halt worker and fire alert.

### 5.5 Parsing the Uber Response

From the Uber fare estimate response, extract the AUTO product only:

```java
// Pseudocode
for tier in response.data.products.tiers:
    for product in tier.products:
        if product.productClassificationTypeName == "AUTO":
            fare = parseFareString(product.fares[0].fare)  // strip ₹, parse float
            meta = parseJson(product.fares[0].meta)
            surgeMultiplier = meta.upfrontFare.dynamicFareInfo.multiplier
            etaMin = product.etaInMin
            // persist record
```

Fields to ignore: all non-AUTO products, `hasPromo`, signatures, `fareSessionUUID`, and other booking-related metadata.

## 6. Eligibility & Dormancy System

### 6.1 Target Samples (X)

- Default: **10 samples per pair per timeslot**
- Configurable at runtime via `POST /api/config/threshold` — no redeployment needed
- Stored in the `config` table as `target_samples_per_slot`

### 6.2 Pair-Timeslot Lifecycle

```
ACTIVE ──(sample_count >= X)──► DORMANT ──(dormant_until passed)──► ACTIVE
                                    │
                         dormant_until = now() + 14 days
```

- **ACTIVE**: Worker collects for this pair-timeslot when it is the current timeslot
- **DORMANT**: Worker skips this pair-timeslot entirely
- Coordinator resets DORMANT → ACTIVE once `dormant_until` has passed (checked every 10 minutes)

### 6.3 Station Readiness Score

```
readiness = Σ(weight_i × min(count_i / X, 1))  /  Σ(weight_i)

where:
  weight_i = 2 if timeslot i is rush hour (slots 2–9 or 24–31)
  weight_i = 1 otherwise
  count_i  = sample_count for this pair-timeslot across all pairs for this station
```

A station is **ready** when `readiness >= 0.50`.

The dashboard `/api/dashboard/stations` endpoint returns this score per station.

## 7. Coordinator & Leader Election

### 7.1 Leader Election

Leadership is determined via optimistic locking in Supabase:

```sql
-- Worker attempts to claim leadership
UPDATE workers
SET is_leader = true, leader_ttl = now() + interval '2 minutes'
WHERE worker_id = $1
  AND (
    -- No current leader
    NOT EXISTS (SELECT 1 FROM workers WHERE is_leader = true AND leader_ttl > now())
    -- Or I am already the leader
    OR (is_leader = true AND worker_id = $1)
  );
```

- Leader TTL is **2 minutes**. The leader must renew every 60 seconds.
- If the leader fails to renew (goes down), another worker claims leadership after TTL expires.
- Non-leaders attempt to claim leadership every 30 seconds.

### 7.2 Coordinator Responsibilities

Runs every 60 seconds on the leader:

```
1. Renew leader TTL

2. Detect stale workers:
   SELECT * FROM workers
   WHERE last_heartbeat < now() - interval '5 minutes'
   AND worker_id != this_worker_id;
   → Update their pairs to worker_id = NULL (unassigned)
   → Delete or mark stale worker records

3. Assign unassigned pairs:
   SELECT * FROM pair_eligibility WHERE worker_id IS NULL LIMIT 500;
   → Distribute evenly among healthy workers (round-robin by assigned_pair_count)

4. Reset dormant pairs:
   UPDATE pair_eligibility
   SET status = 'ACTIVE', dormant_until = NULL, sample_count = 0
   WHERE status = 'DORMANT' AND dormant_until < now();
```

### 7.3 Worker Heartbeat

Every worker (including the leader) runs a heartbeat every 60 seconds:

```sql
UPDATE workers
SET last_heartbeat = now(), assigned_pair_count = $count
WHERE worker_id = $id;
```

On startup, workers register themselves:

```sql
INSERT INTO workers (worker_id, last_heartbeat)
VALUES ($id, now())
ON CONFLICT (worker_id) DO UPDATE SET last_heartbeat = now();
```

`worker_id` is generated at startup as `{hostname}-{uuid-short}` and stored in an env var for consistency across restarts on Render.

## 8. Station JSON Hot-reload

### 8.1 Flow

`POST /api/stations/reload` accepts the full `metro_stations.json` body:

```
1. Validate JSON structure (required fields: id, name, line, exits with lat/lng)
2. Upsert into stations + station_exits tables
3. Run H3 hotspot generation logic in-process:
   - For each new/updated exit, compute H3 hex centroids within 2km radius (res-8)
   - Generate pair_ids for new (exit, hotspot, direction) combinations
4. INSERT new pairs into pair_eligibility as ACTIVE + unassigned
   (ON CONFLICT DO NOTHING — existing pairs are untouched)
5. Coordinator picks up unassigned pairs on its next cycle (within 60s)
```

### 8.2 What Doesn't Change on Reload

- Existing `pair_eligibility` rows are not touched — sample counts and dormancy state are preserved
- Existing `fare_records` are not touched
- Workers currently mid-collection are not interrupted

### 8.3 H3 Logic in Java

Add the H3 Java library:

```xml
<dependency>
    <groupId>com.uber</groupId>
    <artifactId>h3</artifactId>
    <version>4.1.1</version>
</dependency>
```

The Java equivalent of the Python H3 script:

```java
H3Core h3 = H3Core.newInstance();
String centerHex = h3.latLngToCellAddress(lat, lng, 8);
List<String> candidates = new ArrayList<>(h3.gridDisk(centerHex, kRings));
candidates.removeIf(hex -> {
    LatLng centroid = h3.cellToLatLng(hex);
    return haversineMeters(lat, lng, centroid.lat, centroid.lng) > 2000;
});
```

## 9. Uber API Integration

### 9.1 Endpoint

The reverse-engineered fare estimate endpoint is called with pickup and destination coordinates. Only the AUTO product (`productClassificationTypeName == "AUTO"`) is extracted from the response.

### 9.2 Auth Tokens

- Tokens are session-based and do not appear to rotate on a time schedule
- Stored as environment variables on Render
- On HTTP 401: worker halts immediately, fires alert, waits for manual token refresh via env var update + redeploy
- Future improvement: token refresh endpoint (not in v1 scope)

### 9.3 Request Headers

Mirror a real Uber app session as closely as possible:
- `User-Agent`: real app user agent string
- `x-uber-device`: device fingerprint headers from a real session
- `Cookie` / `Authorization`: captured session tokens
- `Content-Type: application/json`

### 9.4 Consecutive Failure Detection

```java
AtomicInteger consecutiveFailures = new AtomicInteger(0);

// On success:
consecutiveFailures.set(0);

// On failure:
int count = consecutiveFailures.incrementAndGet();
if (count >= config.consecutive_failure_alert_threshold) {
    alertService.sendAlert(AlertType.CONSECUTIVE_FAILURES, count);
    Thread.sleep(Duration.ofMinutes(10)); // pause before resuming
}
```

## 11. Alerting

### 11.1 Alert Conditions

| Condition | Threshold | Action |
|---|---|---|
| Worker heartbeat missed | 5 minutes | Email + coordinator reassigns pairs |
| Consecutive Uber API failures | 20 in a row | Email + worker pauses 10 min |
| HTTP 401 / token invalidation | Any | Email + worker halts, manual intervention required |
| No active collection | 30 minutes | Email if all assigned pairs are DORMANT or no workers healthy |

### 11.2 Alert Deduplication

Alert state is tracked in Supabase to prevent duplicate emails for the same ongoing condition:

```sql
CREATE TABLE alert_state (
    alert_type     VARCHAR(50) PRIMARY KEY,
    fired_at       TIMESTAMPTZ NOT NULL,
    resolved_at    TIMESTAMPTZ,
    is_active      BOOLEAN NOT NULL DEFAULT true
);
```

An alert is only re-fired if the previous one has been resolved (i.e. `is_active = false`).

### 11.3 Email Delivery

Use SendGrid free tier (100 emails/day). Configure via env vars:

```
SENDGRID_API_KEY=...
ALERT_EMAIL_TO=your@email.com
ALERT_EMAIL_FROM=pravah-alerts@yourdomain.com
```
